# ADR 0013: личная дневная цель как read-only проекция activity history

- **Статус:** Accepted for MVP content loop
- **Дата:** 2026-07-26

## Контекст

До этого production home всегда возвращал `dailyGoal = 6000`. Фиксированная цель удобна для первого вертикального среза, но противоречит продуктовой гипотезе Walking RPG: пользователь с обычными 2 000 шагов и пользователь с 18 000 шагов не должны получать одну и ту же планку.

У backend уже есть монотонный accepted total по пользователю и локальному дню в `activity_sync_state`. Это позволяет рассчитывать цель без передачи дополнительных health-данных и без доверия клиенту.

## Решение

Вводится политика `adaptive-median-v1`:

```text
window = 7 локальных календарных дней перед запрошенной датой
validDay = accepted_total > 0
minimumSampleDays = 3
baseline = median(validDays)
nextGoal = roundTo250HalfUp(baseline × 1.05)
dailyGoal = clamp(nextGoal, 2000, 12000)
```

Если валидных дней меньше трёх, используется `defaultGoal = 6000`.

Дополнительные правила:

1. Текущий день не участвует в расчёте собственной цели.
2. Отсутствующая строка activity history означает «нет достоверного чтения», а не ноль шагов.
3. Порядок строк истории не влияет на медиану; для чётного количества дней используется точное среднее двух центральных значений, поэтому `baselineSteps` может оканчиваться на `.5`.
4. Все параметры вынесены в `walking-rpg.daily-goal.*` и могут изменяться без переписывания алгоритма.
5. `GET /api/v1/home` остаётся read-only: таблица snapshot-ов целей в v1 не создаётся.
6. Mobile не вычисляет цель и получает её вместе с прозрачным `dailyGoalPolicy`.

## API

Home response содержит прежнее числовое поле `dailyGoal` и новый объект:

```json
{
  "dailyGoal": 3250,
  "dailyGoalPolicy": {
    "policyVersion": "adaptive-median-v1",
    "source": "ADAPTIVE",
    "baselineSteps": 3000,
    "sampleDays": 3,
    "lookbackDays": 7,
    "minimumSampleDays": 3,
    "defaultGoal": 6000,
    "growthPercent": 5,
    "roundingStep": 250,
    "minimumGoal": 2000,
    "maximumGoal": 12000
  }
}
```

Для cold start `source = DEFAULT`, а `baselineSteps = null`. Flutter на время rolling deploy принимает response без `dailyGoalPolicy` как legacy response и не пытается восстановить формулу локально.

## Почему медиана

Медиана менее чувствительна к одному аномально активному или неактивному дню, чем среднее. Это полезно до появления полноценного risk score и не требует собирать сырые health samples.

## Почему цель пока не сохраняется

Постоянный goal snapshot сделал бы цель стабильной при поздней коррекции прошлых шагов, но потребовал бы решить, какая команда создаёт snapshot, не превращая read-only `GET /home` в write-операцию и не вводя ночной scheduler по часовым поясам.

На v1 цель является детерминированной read-проекцией. Поэтому поздний sync или удаление записи за прошлый день может изменить цель текущего дня. Это осознанная граница; snapshot persistence рассматривается после device validation и первых продуктовых данных.

## Последствия

Плюсы:

- реализована ключевая продуктовая гипотеза без новых персональных данных;
- цель принадлежит backend и не подменяется клиентом;
- cold start остаётся предсказуемым;
- параметры готовы к экспериментам;
- `GET /home` не создаёт строки и не требует миграции БД.

Ограничения:

- цель может измениться после поздней коррекции предыдущего дня;
- пропущенные дни не участвуют в baseline, поскольку backend не отличает отсутствие прогулки от отсутствия sync;
- milestone rewards 25/50/75/100/120% пока не реализованы;
- отдельная пользовательская настройка доступности и медицинские рекомендации не входят в политику.
