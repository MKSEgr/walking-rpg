# ADR 0004: накопительный authoritative total и идемпотентная синхронизация активности

- **Статус:** принято
- **Дата:** 2026-07-25

## Контекст

Apple Health и Health Connect могут возвращать агрегированное число шагов за интервал. Клиент способен повторять запрос после таймаута, переустановки соединения или фоновой синхронизации. Если backend будет принимать произвольную «дельту шагов» от клиента, повтор запроса сможет создать двойную награду, а частые синхронизации будут сложнее сверять.

Один пользователь также может открыть приложение на нескольких устройствах. Если вести отдельный reward high-watermark для каждой установки, одинаковая дневная активность сможет быть начислена повторно.

## Решение

1. Клиент передаёт накопительный `authoritativeTotal` за локальный календарный день, а не запрашивает начисление конкретной дельты.
2. Backend хранит максимальный принятый total для пары пользователь + локальный день. Устройство остаётся частью идентификации запроса и idempotency scope, но не создаёт отдельный пул награды.
3. Total разных устройств не суммируется. Для MVP принимается только рост общего user-level high-watermark.
4. Допустимая дельта рассчитывается как `max(0, authoritativeTotal - acceptedTotal)`.
5. Уменьшение системного total не уменьшает игровой баланс и возвращает диагностический статус `TOTAL_DECREASED`.
6. Каждая команда содержит `idempotencyKey`. Повтор идентичной бизнес-команды возвращает исходный результат. Повтор ключа с другим payload возвращает конфликт.
7. Attestation не входит в business fingerprint: он может быть перевыпущен при сетевом повторе и должен проверяться отдельно для каждого запроса.
8. Начисление энергии считается по пересечённым накопительным порогам:

```text
energyGranted = floor(newAcceptedTotal / stepsPerEnergy)
              - floor(previousAcceptedTotal / stepsPerEnergy)
```

Это сохраняет остаток шагов между частыми синхронизациями. Например, total `99`, затем `100` выдаёт одну единицу энергии.

9. До любой state mutation backend вычисляет текущую локальную дату из
   `serverTime` и заявленной IANA `timeZone`. Запрос с более поздней
   `localDate` отклоняется как `VALIDATION_ERROR`; прошлые даты остаются
   допустимыми для безопасного повтора сохранённой команды после полуночи.
   Request boundary принимает только ID из установленного IANA/TZDB registry;
   произвольные fixed offsets вроде `+18:00` отклоняются до date validation.

## Persistence

Первый prototype использовал память процесса. Persistent vertical slice заменяет его на PostgreSQL/Flyway и выполняет state update вместе с сохранением idempotent response в одной транзакции. Конкурирующие запросы одного пользователя сериализуются user-level advisory transaction lock.

До появления аутентификации и реестра устройств идентификаторы временно передаются заголовками `X-User-Id` и `X-Device-Id`. Клиентский `userId` в request body не вводится, чтобы не закреплять доверие к пользовательскому идентификатору из тела запроса.

## Последствия

### Положительные

- повтор запроса не создаёт повторную награду;
- два устройства не получают независимую награду за один дневной total;
- сервер, а не клиент, вычисляет дельту и энергию;
- частота синхронизации не влияет на накопление остатка шагов;
- понижение данных Health API диагностируется без отрицательной экономики;
- будущая локальная дата не может создать отдельный дневной high-watermark или
  начислить ENERGY;
- state и idempotent response сохраняются после перезапуска.

### Ограничения

- user-level lock сериализует все устройства пользователя;
- MVP использует максимум cumulative total, а не объединяет независимые шаги разных экосистем;
- attestation пока принимается, но не проверяется;
- buckets пока используются только как часть идемпотентного payload и не участвуют в антифроде;
- энергия ещё не записывается в ledger и не двигает экспедицию.
