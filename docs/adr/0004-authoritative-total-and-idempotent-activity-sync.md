# ADR 0004: накопительный authoritative total и идемпотентная синхронизация активности

- **Статус:** Accepted for the activity-sync spike
- **Дата:** 2026-07-25

## Контекст

Apple Health и Health Connect могут возвращать агрегированное число шагов за интервал. Клиент способен повторять запрос после таймаута, переустановки соединения или фоновой синхронизации. Если backend будет принимать произвольную «дельту шагов» от клиента, повтор запроса сможет создать двойную награду, а частые синхронизации будут сложнее сверять.

## Решение

1. Клиент передаёт накопительный `authoritativeTotal` за локальный календарный день, а не запрашивает начисление конкретной дельты.
2. Backend хранит максимальный принятый total для пары пользователь + устройство + локальный день.
3. Допустимая дельта рассчитывается как `max(0, authoritativeTotal - acceptedTotal)`.
4. Уменьшение системного total не уменьшает игровой баланс и возвращает диагностический статус `TOTAL_DECREASED`.
5. Каждая команда содержит `idempotencyKey`. Повтор идентичной команды возвращает исходный результат. Повтор ключа с другим payload возвращает конфликт.
6. Начисление энергии считается по пересечённым накопительным порогам:

```text
energyGranted = floor(newAcceptedTotal / stepsPerEnergy)
              - floor(previousAcceptedTotal / stepsPerEnergy)
```

Это сохраняет остаток шагов между частыми синхронизациями. Например, total `99`, затем `100` выдаёт одну единицу энергии.

## Временная граница spike

В первой реализации состояние хранится в памяти процесса, чтобы проверить контракт и доменные инварианты без преждевременного проектирования постоянной схемы. Она не предназначена для нескольких backend-инстансов и теряется после перезапуска.

Следующий persistent vertical slice должен заменить in-memory repository на PostgreSQL/Flyway и обеспечить атомарность через ограничения БД и транзакцию, не меняя доменную семантику контракта.

До появления аутентификации и реестра устройств идентификаторы временно передаются заголовками `X-User-Id` и `X-Device-Id`. Клиентский `userId` в request body не вводится, чтобы не закреплять доверие к пользовательскому идентификатору из тела запроса.

## Последствия

### Положительные

- повтор запроса не создаёт повторную награду;
- сервер, а не клиент, вычисляет дельту и энергию;
- частота синхронизации не влияет на накопление остатка шагов;
- понижение данных Health API диагностируется без отрицательной экономики;
- контракт можно сохранить при переходе на PostgreSQL.

### Ограничения

- текущее `synchronized` и in-memory состояние подходят только одному процессу;
- не решено объединение данных нескольких устройств одного пользователя;
- attestation пока принимается, но не проверяется;
- buckets пока используются только как часть идемпотентного payload и не участвуют в антифроде;
- энергия ещё не записывается в ledger и не двигает экспедицию.
