# ADR 0007: production home как read-only projection activity и economy

- **Статус:** Accepted for first playable
- **Дата:** 2026-07-25

## Контекст

После появления persistent activity state и ENERGY ledger мобильному приложению нужен один запрос, который возвращает актуальное состояние главного экрана. Возвращать только результат последнего activity command недостаточно: идемпотентный command response намеренно хранит исторический snapshot, а главный экран должен показывать самый новый баланс.

Одновременно изменяемые pilot/pet/expedition ещё не реализованы. Создавать их таблицы только ради статической карточки преждевременно.

## Решение

1. Добавляется `GET /api/v1/home?localDate=YYYY-MM-DD`.
2. До security слоя пользователь передаётся через обязательный `X-User-Id`.
3. `localDate` передаётся клиентом. Backend не угадывает локальный календарный день по своему часовому поясу.
4. Read-model одним SQL-запросом объединяет:
   - `activity_sync_state` для `userId + localDate`;
   - `economy_wallet` для `userId + ENERGY`.
5. Activity state относится к выбранному дню; ENERGY wallet является текущим и не зависит от дня.
6. Если строки отсутствуют, endpoint возвращает нулевые значения, а не 404.
7. Запрос является read-only и не создаёт `app_user`, wallet или игровые записи.
8. `timeZone` возвращается из activity state и может быть `null`, если за день синхронизации ещё не было.
9. Pilot, pet и expedition пока приходят из server-owned starter content с явным `contentVersion = starter-v1`.
10. Response содержит activity/economy версии и `lastActivitySyncAt`, чтобы mobile мог диагностировать устаревшее состояние.
11. Flutter получает production response через минимальный `dart:io` transport без новой внешней зависимости.
12. Сетевые ошибки на экране видимы: loading, error, retry и явный demo fallback. Silent fallback запрещён.

## Почему endpoint не инициализирует игрока

GET с побочными эффектами усложняет повторяемость, кэширование и расследование ошибок. До появления аутентификации неизвестный `X-User-Id` не должен молча создавать аккаунт.

Будущий onboarding/bootstrap станет отдельной командой. Activity sync пока остаётся единственным источником технической регистрации `app_user`.

## Почему starter content не сохраняется в БД

Пилот, питомец и экспедиция пока не меняются. Отдельные таблицы появятся вместе с первой командой изменения игрового состояния — расходом энергии и продвижением узла. Это сохраняет принцип проекта: миграция появляется вместе с работающей пользовательской функцией, а не заранее.

`contentVersion` позволяет отличить временный starter template от будущего persistent state и безопасно изменить начальную конфигурацию.

## Последствия

Плюсы:

- mobile видит реальные шаги и текущий баланс;
- command/query semantics разделены;
- endpoint не мутирует данные;
- отсутствие пользователя/дня обрабатывается предсказуемо;
- не создаются преждевременные игровые таблицы;
- сетевой слой mobile остаётся dependency-light.

Ограничения:

- `localDate` пока формируется mobile без Health API;
- mobile ещё не вызывает activity sync;
- нет offline cache;
- starter pilot/pet/expedition не имеют индивидуального прогресса;
- IANA time zone берётся только из последнего принятого activity state.
